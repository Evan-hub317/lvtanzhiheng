# 对话式分析 Agent（Function Calling 自主编排）· 可行性分析

日期：2026-09-24

---

## 一、总体结论

**可行，强烈建议实施。** 现有系统已具备全部"被编排能力"（7 类工具对应的接口已上线且验证过），Agent 本质是"LLM 循环 + 工具注册 + 前端可视化"三层增量，**不动现有业务逻辑**，预计 **5~8 天**完成。这是答辩的"临门一脚"亮点：从"人操作系统"升级为"人问系统、系统自己干"。

---

## 二、需求理解与演示场景

**核心场景**：「江苏明年会超标吗？」——Agent 自主执行：

```
提问 → ① 查江苏历史 KPI（总量/强度/上限）
     → ② 调 LSTM 预测明年趋势
     → ③ 对比阈值规则
     → ④ 生成趋势图
     → ⑤ 带结论回答："预计 2026 年江苏排放 11.8 亿吨，超过上限 11.5 亿吨，存在超标风险"
```

全过程前端可视化：每一步的**工具名、参数、执行状态、结果摘要、图表**以时间线形式呈现（"思考过程 + 执行链路"），答辩时评委能看到 Agent"自己动手"。

---

## 三、技术方案

### 3.1 架构：Agent 循环放 Java（推荐）

```
前端（对话界面 + 执行链路面板）
   │ SSE（步骤事件流）
Java AgentService（Agent 循环）
   │ ① 调 DeepSeek（function calling）
   │ ② 执行工具（复用现有 Service：Analysis/Calc/Simulation/Alert/Report）
   └─ 工具结果回填 messages → 再问 LLM → 直到给出最终回答
```

**为什么放 Java**：现有 7 类工具全部是 Java 接口（鉴权、事务、算法服务编排都在 Java 层），Agent 循环放 Java 可直接复用 Service，无需反向调用。Java 直连 DeepSeek API（OpenAI 兼容格式，DeepSeek 官方支持 `tools` 参数）。

### 3.2 Agent 循环（标准 ReAct 模式，上限 6 轮）

```
第 1 轮：system（角色+工具说明）+ user 问题 → LLM 返回 tool_call
第 2 轮：tool_call 结果回填 → LLM 继续 tool_call 或输出最终回答
...（循环）
终止：LLM 输出最终回答（带结论）或达到轮次上限（强制要求总结）
```

### 3.3 前后端交互协议（SSE 事件流）

| 事件类型 | 载荷 | 前端呈现 |
|---|---|---|
| `tool_call` | {name, args} | 时间线新增"正在调用：查询江苏KPI" |
| `tool_result` | {name, summary, durationMs, chart?} | 状态变为 ✅ + 结果摘要；chart 存在则渲染图表 |
| `answer_delta` | {content} | 最终回答打字机流式输出 |
| `done` | {} | 会话结束 |

### 3.4 工具注册清单（7 个工具 = 现有接口包装）

| 工具名 | 包装的现有接口 | 参数 | 返回 |
|---|---|---|---|
| `query_kpi` | /analysis/kpi | region 名称 | 总量/同比/碳强度 |
| `query_trend` | /analysis/trend | region、年份范围 | 年度序列 + **chart 指令**（趋势图） |
| `query_structure` | /analysis/structure | region、年 | 行业结构 + chart（饼图） |
| `run_calc` | /calc/execute | 年份范围 | 核算行数/校准报告 |
| `predict_emission` | /sim/predict | region | 预测轨迹 + chart（含置信区间） |
| `detect_anomaly` | /alert/anomaly | — | 异常点 Top N + chart（散点标注） |
| `simulate_policy` | /sim/simulate | region、煤/工业/能效参数 | 仿真轨迹 + chart + 达峰 |
| `generate_report` | /report/generate | region、期型 | 报告标题/正文 |

**图表机制**：工具返回数据时附带 `chart: {type, option}`（ECharts option 序列化 JSON，数据量小：趋势 5-6 点、结构 5 类），前端用既有渲染逻辑直接出图——不需要图片传输。

### 3.5 关键实现细节

- **区域名称 → ID 映射**：工具参数用中文名（"江苏"），Java 内查 dim_region 转换（防 LLM 幻觉出 ID）
- **阈值对比**：Agent 在提示词中获知平台预警规则（如"年度总量上限"），让 LLM 自己对比预测值与阈值并下结论；**更稳做法**：加第 9 个工具 `check_threshold(region, year)` 由后端返回"是否超标"结论，避免 LLM 算错
- **DeepSeek 配置**：复用系统环境变量 DEEPSEEK_API_KEY（Java 进程同样可读）；base-url 入 application.yml

## 五、风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| DeepSeek function calling 偶尔不触发工具/参数幻觉 | 中 | 工具描述写详细示例；参数用中文名称+后端映射；轮次上限 6 强制总结 |
| 长任务工具超时（核算 2 分钟） | 中 | SSE 心跳事件（每 10 秒 `heartbeat`）；前端超时 3 分钟；核算工具提示"预计耗时" |
| 多轮调用 token 成本/延迟 | 低 | 单次对话约 3-6 次 LLM 调用，DeepSeek 单价低；循环上限控制 |
| LLM 对比阈值算错 | 中 | 增加 `check_threshold` 后端工具（结论由代码给出，LLM 只负责表述） |
| 图表数据过大 | 低 | 工具只回传聚合点（≤12 个），前端渲染 |

## 七、待确认决策

1. **入口位置**：独立菜单页「AI 分析助手」（推荐）还是嵌入现有 AI 碳管家页？
2. **阈值语义**：`check_threshold` 用平台预警规则（6 亿吨全国上限）还是允许在提问中指定阈值（如"按 11 亿吨算"）？推荐：两者都支持，提问未指定时用平台规则。
3. **工具数量**：9 个工具（含 check_threshold）还是先做 7 个核心（查询/预测/仿真/异常/报告）？推荐 9 个一次到位。
4. **会话落库**：复用 chat 表（是）还是独立 agent_session 表（更清晰，推荐独立但仅 1 张表）。

## 八、答辩话术（预留）

> 平台不只"会算"，还"会做"——用户用自然语言提问，AI 自主决定调用哪些分析工具、按什么顺序执行，最后给出带证据链的结论。每一步工具调用过程对用户透明可见，这是"可解释的 AI 决策"。
